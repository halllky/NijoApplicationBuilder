# Phase 2: 画面一覧の作成と design/ の責務マトリクス

「nijo.xml + design/」でシステム設計として必要なドキュメントが揃う。
design/ は nijo.xml と同じフォルダ階層に置き、同じバージョン管理ライフサイクルに乗せる。

```
<プロジェクトフォルダ>/
├── nijo.xml               # データ構造・画面項目定義・設計判断の理由（XMLコメント）
└── design/
    ├── requirements.md    # 背景・目的・スコープ・要求一覧 ※ヒアリングが正
    ├── stakeholders.md    # アクター・外部システム・関係者 ※ヒアリングが正
    ├── glossary.md        # 用語集（所与の用語のみ）       ※ヒアリングが正
    ├── usecases.md        # 業務フロー図 + ユースケース     ※ヒアリングが正
    ├── nonfunctional.md   # 非機能要件                     ※ヒアリング原文＋設計値
    ├── screens.md         # 画面一覧                       ※本スキルが正
    ├── handwork.md        # Nijo 生成範囲外の手実装要件     ※本スキルが正
    └── issues.md          # 課題管理表                     ※両スキル共同
```

ヒアリング系ファイルのテンプレートは [nijo-requirement-elicitation の references/10_doc-templates.md](../../nijo-requirement-elicitation/references/10_doc-templates.md) を正とする（issues.md の状態定義もそこにある）。

## 責務マトリクス（最重要ルール）

**nijo.xml またはその派生から表現できる情報は design/ に書かない。** 二重管理は必ず腐る。

| 情報 | 正とする場所 | 本スキルがしてよいこと |
|---|---|---|
| 画面項目定義・入出力項目 | nijo.xml（query-model / structure-model / Parameter） | モデル名による参照のみ。**項目リストの転記禁止** |
| ER図・テーブル定義 | 書かない（生成後の EF Core / DbContext が正） | 何も書かない。集約間の関係は nijo.xml の ref-to が表現する |
| 設計判断の理由（なぜこのキーか、なぜ分割したか） | nijo.xml の XML コメント | 何も書かない |
| 画面のレイアウト・遷移の実装 | 手実装コード（client/src/pages。規約は nijo-frontend-implementation スキル） | 何も書かない。ワイヤーフレーム・項目配置・遷移図は design/ に描かない |
| 要求・スコープ | design/requirements.md | 「落とし先」列の追記のみ（仕様化のトレース） |
| アクター・外部システム・関係者 | design/stakeholders.md | 読むだけ |
| 用語 | design/glossary.md | 読むだけ。**glossary.md は所与の用語（設計側で変更できない既存の業務概念）のみを載せる**。設計で新造した集約名・画面名は載せず、その説明は nijo.xml の XML コメントが正 |
| 業務フロー・ユースケースのシナリオ | design/usecases.md | 一覧への「対応モデル」「対応画面」列の追記のみ |
| 非機能要件 | design/nonfunctional.md | 「設計値・方針」列への追記のみ（ヒアリング原文の列は書き換えない） |
| 画面の構成・編集単位・排他・権限・処理方式 | design/screens.md | **ここが正。本スキルが作成する** |
| Nijo 生成範囲外の手実装要件（外部連携仕様・バッチ・帳票・通知等） | design/handwork.md | **ここが正。本スキルが作成する** |
| 確認事項・未決事項・仮定 | design/issues.md | 起票・状態更新（仮定は「仮置き」で起票） |

ヒアリングが正のファイルの業務内容に誤り・欠落を見つけた場合は、勝手に直さず issues.md に起票してユーザーに確認する。

## screens.md のテンプレート

ユースケースから react.js 実装へ一気にジャンプしない。その中間で「どの集約を・どう操作する画面か」を確定し、ユースケースとの矛盾・網羅性をレビューできるようにするのが画面一覧の役割。画面は全て手実装（client/src/pages）であり、screens.md はその手実装フェーズへの直接の入力になる。

**UIレイアウト（ワイヤーフレーム・項目配置）と画面遷移図は書かない**。項目は nijo.xml が、レイアウトと遷移の実装は手実装コードが正。一覧→詳細のような定型遷移は書くまでもなく、業務上意味のある特殊な遷移（例: 締め完了後に必ず確認画面を挟む）のみ備考に書く。

### 記入タイミング（Phase をまたぐ）

- **Phase 2（モデル設計前）**: ID・画面・種別・対応UC・利用可能ロール・編集単位・処理方式・備考を記入し、ユーザー承認を得る
- **Phase 3（モデル設計後）**: 対象集約（操作）・排他 の2列を埋めてからレビューAに入る。集約が決まる前にこの2列を推測で埋めない

```markdown
# 画面一覧

| ID | 画面 | 種別 | 対応UC | 利用可能ロール | 対象集約（操作） | 編集単位 | 排他 | 処理方式 | 備考 |
|---|---|---|---|---|---|---|---|---|---|
| SC01 | 売上一覧 | 一覧 | UC02 | A1, A2 | 売上（閲覧） | - | - | 同期 | query-model: 売上一覧 |
| SC02 | 売上登録 | 登録 | UC01 | A1, A2 | 売上（作成）、在庫（更新） | 1件 | 楽観 | 同期 | command-model: 売上新規登録 |
| SC03 | 棚卸入力 | 編集 | UC05 | A2 | 在庫（更新） | 一括 | 楽観（集約単位） | 同期 | |
| SC04 | 月次締め | 実行 | UC06 | A2 | 売上・在庫（更新） | 一括 | 実行中は締め対象の更新を拒否 | 非同期（バッチ） | 処理時間が長いため |

## 凡例

- **種別**: 一覧 / 詳細 / 登録 / 編集 / 実行（コマンド起動） / 帳票 / 設定 / その他
- **対応UC**: usecases.md の UC ID
- **利用可能ロール**: stakeholders.md のアクター ID で記載。全アクター共通なら「全員」。権限差の正はこの列（アクター×画面のマトリクスが必要なほど複雑な場合のみ別表を起こす）
- **対象集約（操作）**: どの DataModel を閲覧するのか更新するのか。1画面が複数集約に触るならすべて列挙 ※Phase 3 で記入
- **編集単位**: 1件ずつか、一覧上で複数件を一括か
- **排他**: 楽観（Nijo標準） / 悲観相当の運用制約 / 排他不要（参照のみ）。標準の楽観排他で足りない場合は方針を書く ※Phase 3 で記入
- **処理方式**: 同期（リアルタイム応答） / 非同期（バックエンドに投げて後で結果確認）。非同期にする場合は理由を備考に書く

## 画面を設けないと判断したユースケース

| UC | 理由 |
|---|---|
| UC00 商品マスタ取込 | 外部システムからの自動連携。実行状況は SC90 で確認する |
```

### 網羅性チェック（screens.md 作成時に必ず行う）

- 全ユースケースが「対応画面あり」または「画面を設けない（理由付き）」のどちらかに落ちているか
- 全画面が少なくとも1つの UC に対応しているか（要求の裏付けのない画面はないか）
- 1つの集約に対して、参照する画面はあるが投入経路（登録・連携）がない、またはその逆になっていないか（Phase 3 の列記入後に確認）
- アクター間に権限差がある場合、利用可能ロール列がそれを表現しているか

### 考慮が漏れやすい画面のチェックリスト

要求に明示されなくても、業務システムとして通常必要になる画面。**要否を必ず検討し**、設ける場合は一覧に追加、設けない場合もその判断を issues.md または備考に残す:

- ログイン・ユーザー管理・権限設定（アクターに権限差がある場合はほぼ必須）
- 各マスタのメンテナンス画面（外部連携マスタも、緊急修正用の手入力経路が要るか検討）
- システム設定（締め日・消費税率など運用中に変わる値の変更画面）
- お知らせ・リリースノート（利用者への周知手段）
- バッチ・外部連携の実行状況/エラー確認画面（非同期処理がある場合はほぼ必須）
- 監査ログ・操作履歴の閲覧画面（監査要件がある場合）

## handwork.md のテンプレート

Nijo の自動生成でカバーされない要件の台帳。**設計から暗黙に消えることを防ぐ**のが目的。Phase 3 の「モデル割当て方針メモ」のうち、生成範囲外の要件リストはここに永続化する（方針メモ自体はセッションで揮発してよい）。

実装の詳細設計（クラス構造・処理ロジック）は書かない。それは実装フェーズ（nijo-backend-implementation / nijo-frontend-implementation）の仕事。ここには「何を・なぜ手実装するか」と、実装者が知らないと困る業務上の決め事だけを書く。

```markdown
# Nijo 生成範囲外の手実装要件

## 外部連携

| ID | 連携 | 相手（stakeholders） | 方式・フォーマット | エラー・リトライ・冪等性の方針 | 対応UC/画面 |
|---|---|---|---|---|---|
| HW01 | 商品マスタ取込 | E1 | CSV / 日次 5:00 ファイル連携 | 再送されたら外部キーで上書き（冪等）。形式エラー行はスキップし SC90 に表示 | UC00, SC90 |

## バッチ・非同期処理

| ID | 処理 | 起動契機 | 処理概要・所要時間の見込み | 失敗時の扱い | 対応UC/画面 |
|---|---|---|---|---|---|
| HW02 | 月次締め | SC04 から手動起動 | 対象月の売上を集計・確定。数分〜 | 全件ロールバックして再実行可能にする | UC06, SC04 |

## 帳票・出力

| ID | 帳票 | 出力契機・形式 | 特記事項 | 対応UC/画面 |
|---|---|---|---|---|

## 通知・その他

| ID | 要件 | 内容 | 対応UC/画面 |
|---|---|---|---|
```

- 該当のないセクションは削ってよい
- 「対応UC/画面」列で usecases.md / screens.md と突合できるようにする
- 方針が未確定の項目は issues.md に起票し、この表には「issues #n 参照」と書く

## Phase 2 完了時のユーザー承認

screens.md（Phase 2 時点の列まで）を書き終えたら、以下をユーザーに提示して承認を得る（業務・画面構成の誤解を nijo.xml 執筆前に止める最後の安価なポイント）:

1. 画面一覧（表をそのまま見せる。特に利用可能ロール・非同期の判断）
2. UC↔画面の対応と「画面を設けない」判断
3. **issues.md の「仮置き」一覧**（「違うものがあれば指摘してください」と添える）

修正指示があれば design/ を直してから Phase 3 へ進む。
