# Phase 2: 中間生成物の作成

nijo.xml で表現できない情報を、対象プロジェクトフォルダ内の `design/` に Markdown で残す。
nijo.xml と同じフォルダ階層に置き、同じバージョン管理ライフサイクルに乗せる。

```
<プロジェクトフォルダ>/
├── nijo.xml
└── design/
    ├── wishes.md          # (存在すれば) nijo-requirement-elicitation の成果物。上書きしない
    ├── actors.md          # アクター定義
    ├── usecases.md        # ユースケース一覧・記述
    ├── business-flow.md   # 業務フロー図（mermaid）
    └── assumptions.md     # 置いた仮定・未確認事項
```

`wishes.md` はこのフェーズの入力であり成果物ではない。内容を転記・要約するのではなく、そこから読み取れる要求を actors.md / usecases.md 等に構造化していく。

## 重複禁止マトリクス（最重要ルール）

**nijo.xml またはその派生から表現できる情報は design/ に書かない。** 二重管理は必ず腐る。

| 情報 | 正とする場所 | design/ に書いてよいこと |
|---|---|---|
| 画面項目定義・入出力項目 | nijo.xml（query-model / structure-model / Parameter） | モデル名による参照のみ。**項目リストの転記禁止** |
| ER図・テーブル定義 | 書かない（生成後の EF Core / DbContext が正） | 何も書かない。集約間の関係は nijo.xml の ref-to が表現する |
| 設計判断の理由（なぜこのキーか、なぜ分割したか） | nijo.xml の XML コメント | 何も書かない |
| アクター・権限 | design/actors.md | ここが正 |
| ユースケースのシナリオ（事前条件・フロー・事後条件） | design/usecases.md | ここが正 |
| 業務全体の流れ・部門間の受け渡し | design/business-flow.md | ここが正 |
| 仮定・未確認事項 | design/assumptions.md | ここが正 |
| 要望・願望の原文（ユーザーの言葉のまま） | design/wishes.md（あれば） | 本フェーズ以降は読み取り専用。アクター・ユースケース等に構造化した後の正は上記各ファイル |

## 各ファイルのテンプレート

### actors.md

```markdown
# アクター定義

| ID | アクター | 種別 | 役割・システムとの接点 | 権限の別 |
|---|---|---|---|---|
| A1 | 店舗スタッフ | 人 | 売上の登録・修正を行う | 一般 |
| A2 | 店長 | 人 | 在庫調整・締め処理を行う | 管理者 |
| A3 | 商品マスタ連携 | 外部システム | 商品マスタを日次で送信してくる | - |
```

### usecases.md

一覧表 + 主要ユースケースの記述。**入出力項目は書かない**（nijo.xml が正）。

```markdown
# ユースケース一覧

| ID | ユースケース | アクター | 対応モデル |
|---|---|---|---|
| UC01 | 売上を登録する | A1 | command-model: 売上新規登録 |
| UC02 | 売上を検索する | A1, A2 | query-model: 売上一覧 |

## UC01 売上を登録する

- **事前条件**: 商品マスタが連携済みであること
- **基本フロー**: スタッフが商品と数量を入力し登録する。システムは在庫を引き当てる
- **代替フロー**: 在庫が不足する場合、エラーとして登録を拒否する
- **事後条件**: 売上データと引当が記録され、在庫残数が減る
```

### business-flow.md

mermaid の `flowchart` で全体業務フローを描く。ノードにはユースケース ID を記載し、usecases.md と突合できるようにする。
外部システム連携のやり取りが複雑な場合のみ `sequenceDiagram` を追加してよい。

```markdown
# 業務フロー

​```mermaid
flowchart LR
    ext[外部システム] -->|日次連携| uc00[UC00 商品マスタ取込]
    uc00 --> uc01[UC01 売上登録]
    uc01 --> uc03[UC03 売上取消]
    uc01 --> uc02[UC02 売上検索]
​```
```

### assumptions.md

```markdown
# 仮定・未確認事項

## 置いた仮定（妥当なデフォルトで進めたもの）

| # | 仮定 | 根拠 | 影響範囲 |
|---|---|---|---|
| 1 | 取消は赤黒方式（負数の訂正データを追加）とする | 監査証跡の要望があるため物理削除は不適 | 売上 DataModel |

## 要確認（ブロッカーではないが、いずれユーザー確認が必要なもの）
```

## Phase 2 完了時のユーザー承認

design/ 4ファイルを書き終えたら、以下をユーザーに提示して承認を得る（業務フローの誤解を nijo.xml 執筆前に止める最後の安価なポイント）:

1. アクターとユースケースの一覧（表をそのまま見せる）
2. 業務フロー図（mermaid）
3. **置いた仮定の一覧**（assumptions.md の内容。「違うものがあれば指摘してください」と添える）

修正指示があれば design/ を直してから Phase 3 へ進む。
