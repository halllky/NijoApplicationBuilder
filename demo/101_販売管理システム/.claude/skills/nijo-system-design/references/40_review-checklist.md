# レビューA / レビューB チェックリストとサブエージェント運用

レビューは必ず **サブエージェント（Agent ツール、general-purpose）** で行う。
設計者（メインの会話）の思い込みを持ち込ませないため、**会話履歴・設計経緯は渡さず、成果物ファイルのパスだけを渡す**。

## 重大度の定義

| 重大度       | 基準                                                       | 設計者側の義務                                                    |
| ------------ | ---------------------------------------------------------- | ----------------------------------------------------------------- |
| **Blocker**  | 要件の欠落・矛盾、DataModel 境界の誤り、業務が回らない構造 | 必ず修正して再 validate                                           |
| **Should**   | 品質・運用性を明確に下げるが業務は回る                     | 修正するか、しない理由を XML コメントまたは issues.md に残す      |
| **Consider** | 改善提案                                                   | 任意                                                              |
| **判断不可** | 入力不足（要求ドキュメントの欠落等）で判定不能             | 不足入力を確認。補えないものは issues.md に「未確認」で起票       |

## レビューA: モデル設計レビュー（Phase 3 の後、nijo.xml 執筆前）

入力: ①design/ 一式（requirements / stakeholders / glossary / usecases / nonfunctional / screens / handwork / issues）②モデル割当て方針メモ

### チェックリスト（Yes で合格）

**トレーサビリティ・網羅性**
- [ ] requirements.md の「スコープ内」の要求で、どの UC・画面・モデルにも落ちていないものはないか（落とし先が空のまま放置されていないか）
- [ ] 全ユースケースに対応する command-model または query-model が割当てられているか
- [ ] 全アクターが少なくとも1つのユースケースに登場するか。直接操作しない関係者が必要とするアウトプット（帳票・証跡）が設計に現れているか
- [ ] 業務フロー図の全ノードがユースケース一覧と対応しているか（逆も）
- [ ] 集約名・項目名・画面名が glossary.md の用語と一貫しているか

**画面一覧（screens.md）との突合せ**
- [ ] 全 UC が「対応画面あり」または「画面を設けない（理由付き）」に落ちているか。UC に対応しない画面はないか
- [ ] 「対象集約」「排他」列が全行埋まっているか（Phase 3 完了時点で空欄は Blocker）。対象集約（閲覧/更新）がモデル割当てと矛盾していないか
- [ ] 編集単位（1件/一括）・排他方針が、DataModel の楽観排他の単位と整合しているか（一括編集画面の対象が複数集約に跨って排他が破綻する等）
- [ ] 処理時間が長くなりうる操作（大量一括・締め・帳票）が同期画面のままになっていないか。非同期の場合、実行状況を確認する手段はあるか
- [ ] 考慮が漏れやすい画面（設定・マスタメンテ・お知らせ・連携状況・監査ログ閲覧）の要否が検討されているか（references/10 のチェックリスト）

**DataModel 粒度（Blocker 級）**
- [ ] 各 DataModel は「同時に更新され、楽観排他で1単位としてロックされてよい」範囲か
- [ ] 別々のアクター・タイミングで更新されるデータが1集約に同居していないか（→分割）
- [ ] 独立したライフサイクル（単独検索・他集約からの参照）を持つ children はないか（→別 Root + ref-to 化）
- [ ] 常に一緒に更新されるのに ref-to で分断され、整合性維持が手実装になっていないか（→統合）

**業務フロー妥当性・現行整合**
- [ ] フローに行き止まり（作られるが使われないデータ）・湧き出し（参照されるが作られないデータ）はないか
- [ ] 取消・訂正・返品・締め後修正などの逆方向業務が必要なのに欠けていないか
- [ ] 要求ドキュメントに現行業務の記載がある場合、それと矛盾する手順を強制していないか

**権限・セキュリティ**
- [ ] stakeholders.md の「権限の別」が screens.md の「利用可能ロール」列に反映されているか。権限差が必要なのに全画面「全員」になっていないか

**Nijo 適合性・実装コスト**
- [ ] Nijo の自動生成でカバーされない要件（外部連携詳細・バッチ・帳票・通知等）が handwork.md に落ちているか（暗黙に消えていないか）。handwork.md の各行が UC/画面と突合できるか
- [ ] command-model の Execute 手実装が過大になる構造（1コマンドに業務が詰め込まれ過ぎ）はないか

**課題管理**
- [ ] 設計が依存している論点で、issues.md に「保留」「未確認」のまま残っているものはないか（あれば Blocker）
- [ ] 方針メモ・screens.md・handwork.md に現れた仮定で、issues.md に「仮置き」起票されていないものはないか

## レビューB: スキーマレビュー（validate 通過後）

入力: ①design/ 一式 ②nijo.xml

### チェックリスト（Yes で合格）

**データ活用可能性**
- [ ] 一覧検索が必要なエンティティに query-model または GenerateDefaultQueryModel があるか
- [ ] 集計・分析に必要なキー（日時、区分、ref-to）が正規化されて残っているか
- [ ] 本来 enum / ref-to にすべき情報が description / word に逃がされていないか

**運用容易性**
- [ ] 全マスタの投入経路（手入力 command か外部連携か）が決まっており、コメントで読み取れるか
- [ ] 論理削除（UseSoftDelete）・履歴の要否が判断され、理由がコメントにあるか
- [ ] 採番（sequence）・キー設計が運用（欠番許容等）と矛盾しないか

**セキュリティ・監査・法令（nonfunctional.md と突合）**
- [ ] 個人情報・機微情報の項目にマスキング等の CustomAttribute が定義・付与されているか（不要ならその判断が読み取れるか）
- [ ] 監査証跡・変更履歴の要件がデータ構造として表現されているか
- [ ] 法令・規程上の保存期間と削除方式（物理/論理）が整合しているか

**性能・データ量（nonfunctional.md と突合）**
- [ ] 増加の速いテーブルの一覧・集計が MapToView / 専用 query-model で賄える構造か
- [ ] コード類の StringSearchBehavior の既定は Exact になっているか。Range（コード範囲検索）や部分一致など Exact 以外を指定している場合、その要件上の理由がコメントで読み取れるか。同一意味の項目間で挙動が食い違っていないか

**外部連携・移行（handwork.md と突合）**
- [ ] 外部連携キー（外部システム側 ID）が UniqueConstraints で一意担保されているか
- [ ] handwork.md の外部連携の冪等性方針（再送時の重複排除等）を支えるキー・制約がデータ構造にあるか
- [ ] データ移行がある場合、旧システムコード等の移行用キーが保持されているか

**将来拡張性**
- [ ] 運用中に増減しうる区分が StaticEnum に固定されていないか（→汎用参照テーブル）
- [ ] 混同すると危険な ID・コード類が value-object 化されているか（少なくとも検討されたか）

**記法品質・重複禁止・トレーサビリティ**
- [ ] UniqueId が全要素にあり、重複がないか
- [ ] キー設計・非必須項目・集約境界の理由が XML コメントに残っているか
- [ ] 集約名・項目名が glossary.md の用語と一貫しているか
- [ ] design/ に項目定義・型情報・ER 相当の図が紛れ込んでいないか（責務マトリクス違反）
- [ ] screens.md の各画面の対象集約・対応モデルが nijo.xml の実体と一致しているか（改名・統合の反映漏れ）
- [ ] requirements.md の「落とし先」、usecases.md の「対応モデル・対応画面」列が最終的な nijo.xml・screens.md と一致しているか

```
## 指示
チェックリストを1項目ずつ検査し、違反を以下の書式で全件報告してください。
チェックリスト外でも、要求と成果物の食い違いに気づいたら報告してください。
問題がなければ「指摘なし」と明言してください。
入力の不足（要求ドキュメントの欠落など）により判定できない項目は、推測で埋めずに
重大度「判断不可」として、何が不足しているかとともに報告してください。

### 指摘の書式
- 重大度: Blocker / Should / Consider / 判断不可
- 該当箇所: 集約名・項目名・画面ID（nijo.xml の場合は UniqueId も）
- 指摘: 何が問題か
- 根拠: 要求ドキュメント・チェックリストのどれに反するか
- 修正案: 具体的にどう直すか
```

## 収束条件（設計者側のルール）

- Blocker: 必ず修正 → 再 validate → **再レビューは1回まで**（同じ観点で無限ループしない）
- Should: 修正するか、しない理由を成果物（XML コメントまたは issues.md）に記録
- Consider: 任意。最終報告に「見送った提案」として記載してよい
- 判断不可: 不足していた入力を確認する。設計者側で補えないもの（要求の欠落等）は issues.md に「未確認」で起票し、最終報告に含める
- 2回目のレビューでも Blocker が残る場合は、その旨を最終報告に明記してユーザーの判断を仰ぐ
