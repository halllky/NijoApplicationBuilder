# Phase 1: 要求の構造化と欠落・矛盾検出

未整理の要望・願望レベルのインプットから、システム化に必要な要求を抽出するための観点カタログ。
インプットを読み終えたら、以下の観点を **1つずつ機械的に** 当てて欠落・矛盾を洗い出すこと。
「書かれていないこと」を見つけるのがこのフェーズの仕事であり、書かれていることの整理だけでは不十分。

## 1. 欠落検出の観点

### 1.1 アクター
- このシステムを操作する人・外部システムは誰か。役割（ロール）の区別はあるか
- 「誰かがやるはず」の操作で、担当アクターが決まっていないものはないか
- アクターごとに見てよいデータ・してよい操作の差（権限）が必要か

### 1.2 データのライフサイクル
- 各データについて「誰が・いつ・どうやって作り、変更し、消す（または消さない）」が言えるか
- **作られるが消えないデータ**はないか（無限に増える → 保持期間・アーカイブ・論理削除の要否）
- **参照されるが作られないデータ**（湧き出し）はないか（マスタの投入経路が未定義など）
- **作られるが使われないデータ**（行き止まり）はないか（何のために登録するのか不明）

### 1.3 例外系・逆方向業務
順方向（登録→処理→完了）だけ書かれた要望は必ず疑うこと。業務には必ず逆方向がある。
- 取消・訂正はできるか。訂正は上書きか、赤黒（マイナス訂正）か
- 返品・キャンセル・差し戻しはあるか
- 締め（月次締めなど）の後の修正はどう扱うか
- 途中でやめた場合（一時保存・下書き）は必要か

### 1.4 外部連携
- 連携の**方向**（受け取るのか送るのか）、**頻度**（日次バッチかリアルタイムか）、**形式**
- 同じデータが再送されたときの挙動（冪等性）。外部側のキーで重複排除できるか
- 外部システム側の識別子（外部キー）を保持する必要はないか

### 1.5 データ量・性能
- 主要データの件数規模と増加速度（1日何件増えるか）
- 一覧検索の頻度と、よく使う検索条件は何か
- 大量データを跨いだ集計・分析が要るか（→ DBビューの検討材料）

### 1.6 法令・監査・セキュリティ
- 個人情報・機微情報は含まれるか（→ マスキング、アクセス制限）
- 監査証跡（誰がいつ何を変更したか）は必要か
- 法令・社内規程による保存年限はあるか。物理削除してよいデータか

### 1.7 移行・初期データ
- 現行システム（Excel含む）からのデータ移行はあるか
- 移行するなら、旧システムのコード体系を保持する必要はないか
- マスタの初期データは誰がどうやって入れるか

## 2. 矛盾検出の観点

- **用語の揺れ**: 同じものが複数の名前で呼ばれていないか（「得意先」「顧客」「取引先」）。逆に、同じ名前が違うものを指していないか
- **同一データの複数の真実**: 同じ情報が2箇所で管理される設計になっていないか。なる場合、どちらが正か
- **フローの矛盾**: 「Aの後にB」と「Bの後にA」が両方読み取れる箇所はないか。フローに循環はないか
- **暗黙の前提の衝突**: 要望者が複数いる場合、互いに矛盾する願望が混ざっていないか

## 3. ブロッカー判定基準

検出した欠落・矛盾は必ず以下の2種に分類する。

| 分類 | 基準 | 扱い |
|---|---|---|
| **ブロッカー** | 答えによって **DataModel の境界・キー設計・業務フローの骨格が変わる** もの | AskUserQuestion で確認（**1回にまとめる**） |
| **仮定可能** | どちらに転んでも局所的な修正で済むもの。業務システムの慣例から妥当なデフォルトを置けるもの | 仮定を置いて進み、`design/assumptions.md` に記録。Phase 2 の承認時にまとめて提示 |

ブロッカーの典型例:
- 「受注と出荷は同時か別タイミングか」（→ 集約の分割に直結）
- 「商品はこのシステムで登録するのか外部から連携されるのか」（→ マスタの投入経路とキー設計に直結）
- 「複数拠点・複数組織を扱うか」（→ ほぼ全テーブルのキーに影響）
- 「取消は物理削除か赤黒か」（→ データ構造に直結）

仮定可能の典型例:
- 表示名・画面の細かい項目の有無
- 備考欄の要否（付けておけばよい）
- 検索条件の細部（StringSearchBehavior など）

### 質問のルール
- 質問は **モデル構造を左右するブロッカーのみ**。1度の AskUserQuestion にまとめる（最大4問）。乱発禁止
- 各質問には「なぜ聞くのか（答えで何が変わるのか）」を description に書く
- 推奨案がある場合は先頭の選択肢に「（推奨）」を付ける
- 4つを超えるブロッカーがある場合は、影響の大きい順に4つを聞き、残りは仮定を置いて assumptions.md に「要確認」として記録する
