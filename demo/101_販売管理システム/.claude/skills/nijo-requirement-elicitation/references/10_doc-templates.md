# design/ 要求ドキュメントのテンプレート

対話で得られた内容をユーザーの言葉のニュアンスを保ったまま構造化する。**AIの解釈で言い換えすぎない。**

共通の注意:
- 話題に出なかったセクション・行は**作らない**（無理に埋めない）。埋まっていないこと自体は issues.md が管理する
- ユーザーの言葉を尊重する。用語を勝手に統一・言い換えしない。揺れに気づいたらユーザーに確認し、結果を glossary.md に記録する
- 画面項目・データ型・テーブル設計など、設計に関わる内容は書かない（nijo-system-design の責務）

## requirements.md — 背景・目的・スコープ・要求一覧

要望は「ふわっとした願望 → スコープとして確定 → 仕様に落ちる」と成熟していく。このファイルはその**全過程を1箇所でトレースする**。願望段階のものも消さずに状態で管理する。

```markdown
# 要求

## 背景・動機

なぜこのシステムが欲しいのか。困っていること。（ユーザーの発言をベースに記述）

## スコープ

- **対象とする業務**: （確定した範囲）
- **対象外とする業務**: （やらないと決めたこと。理由もあれば）

## 要求一覧

| ID | 要求 | 出所 | 状態 | 落とし先 |
|---|---|---|---|---|
| R-01 | 売上をその場で登録したい | 店長ヒアリング | 仕様化済み | UC01, SC02 |
| R-02 | 月次の売れ筋分析がしたい | 店長ヒアリング | スコープ内 | （設計待ち） |
| R-03 | ゆくゆくはECとも連携したい | 社長の雑談 | 願望 | - |
| R-04 | 会計システムへの自動仕訳 | 経理部 | 対象外 | issues #3（次期検討） |

状態: 願望（まだ言葉になりきっていない） / スコープ内（今回やると確定） / 対象外（やらないと確定） / 仕様化済み（usecases・screens・nijo.xml に落ちた。落とし先に ID を記載）
```

- 「落とし先」列は nijo-system-design が仕様化のたびに更新する。elicitation の段階では空でよい
- 願望・対象外も**削除しない**。経緯が消えると後で必ず蒸し返される

## stakeholders.md — アクター・外部システム・関係者

システムを直接操作するアクターだけでなく、**外部システム**と、**直接操作しないが影響を受ける・関心を持つ関係者**も記録する。

```markdown
# 関係者定義

## アクター（システムを直接操作する人・部署）

| ID | アクター | 役割・システムとの接点 | 権限の別 |
|---|---|---|---|
| A1 | 店舗スタッフ | 売上の登録・修正を行う | 一般 |
| A2 | 店長 | 在庫調整・締め処理を行う | 管理者 |

## 外部システム

| ID | システム | 連携内容 | 方向 | 頻度 |
|---|---|---|---|---|
| E1 | 商品マスタ連携 | 商品マスタを受信する | 受信 | 日次 |

## その他の関係者（直接操作しないが影響を受ける・関心を持つ人）

| ID | 関係者 | 関わり方 |
|---|---|---|
| S1 | 経営層 | 月次の売上レポートを受け取る（本人は操作しない） |
| S2 | 監査部門 | 年次監査で操作証跡の提出を求める |
```

## glossary.md — 用語集

そのシステム・業務に特有の言葉。社内用語・業界用語・略語・「一般的な意味と違う使われ方をしている言葉」を記録する。

**所与の用語（設計側で変更できない、業務に既に存在する概念）のみを載せる。** 設計で新しく作った集約名・画面名・区分名は載せない（それらの説明は nijo.xml の XML コメントが正）。逆に、設計はここに載った用語に従う。

```markdown
# 用語集

| 用語 | 意味 | 備考・揺れ |
|---|---|---|
| 赤黒 | 誤った伝票を負数の伝票で打ち消し、正しい伝票を立て直す訂正方式 | |
| 得意先 | 継続取引のある法人顧客 | 「顧客」「取引先」と呼ぶ人もいる。本システムでは「得意先」に統一（ユーザー確認済み） |
```

- 用語の統一はユーザーが決める。AIが勝手に決めない。未確認の揺れは issues.md に起票する
- ここに載った用語は以後の全ドキュメント・nijo.xml の集約名/項目名で一貫して使う

## usecases.md — 業務フロー + ユースケース

業務全体の流れ（フロー図）と、システムとの接点1回分の記述（ユースケース）を**1ファイルに同居**させ、乖離を防ぐ。フロー図のノードにはユースケース ID を記載し、必ず突合できるようにする。

**入出力項目は書かない**（nijo.xml が正）。

```markdown
# 業務フローとユースケース

## 業務フロー

業務全体の流れ。部門間・外部システムとの受け渡しを含む。システム外の作業（紙・電話等）も含めてよい（その場合はノードに UC ID を付けない）。

​```mermaid
flowchart LR
    ext[E1 商品マスタ連携] -->|日次| uc00[UC00 商品マスタ取込]
    uc00 --> uc01[UC01 売上登録]
    uc01 --> uc03[UC03 売上取消]
    uc01 --> uc02[UC02 売上検索]
​```

外部システム連携のやり取りが複雑な場合のみ `sequenceDiagram` を追加してよい。

## ユースケース一覧

| ID | ユースケース | アクター | 頻度・タイミング |
|---|---|---|---|
| UC01 | 売上を登録する | A1 | 随時（1日数十件） |
| UC02 | 売上を検索する | A1, A2 | 随時 |

## UC01 売上を登録する

- **事前条件**: 商品マスタが連携済みであること
- **基本フロー**: スタッフが商品と数量を入力し登録する。システムは在庫を引き当てる
- **代替フロー**: 在庫が不足する場合、エラーとして登録を拒否する
- **事後条件**: 売上データと引当が記録され、在庫残数が減る
```

- 一覧の全 UC がフロー図に現れること（逆も）。記述は主要 UC のみでよい
- ※一覧表の「対応モデル」「対応画面」列は nijo-system-design が設計時に追記する。elicitation の段階では書かない

## nonfunctional.md — 非機能要件

ヒアリング原文（ユーザーの体感ベースの言葉）と設計値を**列で分離**する。
「ヒアリング（原文）」列は nijo-requirement-elicitation が記入し、以後書き換えない（ヒアリングが正）。
「設計値・方針」列は nijo-system-design が記入する（原文を根拠として数値・方針に正規化する。elicitation の段階では空欄のまま）。

```markdown
# 非機能要件

## 性能・データ量

| 観点 | ヒアリング（原文） | 設計値・方針（nijo-system-design が記入） |
|---|---|---|
| 主要データの件数規模・増加速度 | 「売上は1日200件くらい。5年は見たい」 | 売上 約7.3万件/年 × 5年保存 → 論理削除+アーカイブ不要と判断 |
| 同時利用者数・ピーク | 「月末の締め日はみんな一斉に使う」 | ピーク同時 30 ユーザー想定 |
| 応答が遅いと困る操作 | 「レジ横で客を待たせられない」 | 売上登録は同期・応答 1 秒以内目標 |

## 可用性・運用時間

| 観点 | ヒアリング（原文） | 設計値・方針 |
|---|---|---|
| 業務時間・止まってはいけない時間帯 | | |
| 障害時にどこまで戻れれば業務が成り立つか | | |

## セキュリティ・監査

| 観点 | ヒアリング（原文） | 設計値・方針 |
|---|---|---|
| 個人情報・機微情報の有無と扱い | | |
| 操作証跡（誰がいつ何をしたか）の要否 | | |

## 法令・保存期間

| 観点 | ヒアリング（原文） | 設計値・方針 |
|---|---|---|
| 法令・社内規程による保存年限、証跡提出義務 | | |

## 運用

| 観点 | ヒアリング（原文） | 設計値・方針 |
|---|---|---|
| バックアップ・リリース作業の制約、監視の要否 | | |
```

- ヒアリングで話題に出なかった観点の行は空欄のままでよい（無理に聞き出さない。設計がその値に依存する場合は nijo-system-design が issues.md 経由で確認する）

## issues.md — 課題管理表（両スキル共同）

AIからユーザーへの確認事項・保留になった論点・AIが置いた仮定を、**セッションをまたいで**管理する台帳。会話の中で出た「あとで確認」はセッション終了で揮発する——必ずここに起票する。

```markdown
# 課題管理表

| # | 起票日 | 論点 | 状態 | 経緯・結論 | 影響範囲 |
|---|---|---|---|---|---|
| 1 | 2026-07-05 | 締め処理後の訂正は可能か | 保留 | ユーザー「経理と相談しないと決められない」 | 売上・締めの設計全体 |
| 2 | 2026-07-05 | 取消は物理削除か赤黒か | 確定 | 赤黒方式。監査証跡の要望のため（2026-07-05 ユーザー回答） | 売上 DataModel |
| 3 | 2026-07-06 | 取消は当日中のみに制限するか | 仮置き | 制限なしと仮定して設計を進行中。承認待ち | UC03 |
```

状態の定義:

| 状態 | 意味 | 起票者 |
|---|---|---|
| **未確認** | ユーザーにまだ聞けていない・回答待ち | 両スキル |
| **保留** | ユーザーが「今は決めない」と明言した未決事項 | 両スキル |
| **仮置き** | AIが仮定を置いて設計を進めている。ユーザー承認待ち | nijo-system-design のみ |
| **確定** | 結論が出て、本文（該当ドキュメント・nijo.xml）に反映済み | 両スキル |
| **取下げ** | 前提が消えて論点自体が不要になった | 両スキル |

運用ルール:
- 「確定」にするのは**結論を本文に反映してから**。issues.md 自体は台帳であり、要求・設計の正ではない
- 確定・取下げの行も削除しない（経緯が財産）
- nijo-requirement-elicitation は「仮置き」を使わない（仮定を置くことがそもそも禁止のため）
- セッション開始時は必ずこのファイルを読み、「未確認」「保留」を対話・設計再開の起点にする
```
