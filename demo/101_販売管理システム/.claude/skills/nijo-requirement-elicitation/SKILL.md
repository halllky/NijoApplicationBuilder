# 要求の聞き出し（要望・願望 → 要求ドキュメントの構造化）

未整理の要望・願望レベルのインプットを、ユーザーと対話しながら `design/` 配下の**要求ドキュメント群**に構造化する。

**このスキルはヒアリング専門である。** ここで作るドキュメントはすべて「ユーザーへのヒアリング結果が正」となるもの。ヒアリング結果から設計（画面一覧・データモデル・nijo.xml）を起こす作業は [nijo-system-design](../nijo-system-design/SKILL.md) の責務であり、このスキルは一切踏み込まない。

## 成果物（このスキルが正を持つファイル）

→ テンプレートは **`references/10_doc-templates.md`** を読む

```
<プロジェクトフォルダ>/design/
├── requirements.md    # 背景・目的・スコープ・要求一覧
├── stakeholders.md    # アクター・外部システム・その他の関係者
├── glossary.md        # 用語集（そのシステム・業務に特有の言葉）
├── usecases.md        # 業務フロー図 + ユースケース一覧・記述
├── nonfunctional.md   # 非機能要件
└── issues.md          # 課題管理表（※両スキル共同。ここでは起票と回答反映を行う）
```

対話は複数セッションにまたがってよい。**セッション開始時に design/ の既存ファイルと issues.md を必ず読み、続きから再開する**（ゼロから聞き直さない）。

## 最重要原則（他のどのルールより優先する）

**ゴールの基準は「設計が完成すること」ではなく「ユーザーが出したい情報を全部出し切ること」。**

- 欠落・矛盾を見つけたら、AIが妥当な仮定を置いて埋めることは**禁止**。必ずユーザーに問い、ユーザー自身の頭で定義させる
- ユーザーが「わからない」「今は決めない」「後で考える」と答えたら、issues.md に**ステータス「保留」で起票し**、それ以上追わない。デフォルト値や推測で埋めない
- 完了の判定はユーザーが行う。「これで話したいことは全部話した」とユーザーが言うまでは終わらない。逆に、観点カタログ上まだ埋まっていない項目があっても、ユーザーが「もう十分」と言えばそこで終了してよい（不完全なまま終わってよい。埋まらなかった観点は issues.md に残す）
- 画面レイアウト・データモデル・nijo.xml でどう表現するか等、設計の話は一切しない。あくまで「ユーザーの頭の中にある業務と要求を言葉にして引き出す」ことに徹する。ただし業務フロー・ユースケース（誰が・何のために・どういう流れで使うか）は業務の事実であり、ヒアリング対象である

## ワークフロー

### Phase 0: 出力先の確認と再開

出力先プロジェクトフォルダ（`design/` の置き場所）をユーザーに確認する。既存の `design/` があれば全ファイルを読み込む。特に issues.md の「未確認」「保留」の課題は、対話再開のネタとして最優先で使う。

### Phase 1: インプット読解

提供された要望・メモ・会話・資料を形式を問わずすべて読む。この時点でユーザーに質問はしない。

### Phase 2: 未言及トピックの検出

→ **`references/00_topics.md` を読む**

観点カタログを1つずつ当てて、「ユーザーがまだ一度も触れていないトピック」を洗い出す。
ここでの目的は欠落を「判定」して埋めることではなく、**質問のネタを見つけること**。

### Phase 3: 対話

見つけたトピックについて、ユーザーに問いかける。

- 1トピックにつき1〜数問。**尋問にならないよう**、自然な会話として問いかける。全観点を機械的に一度に浴びせない
- ユーザーの回答は言い換えず、意味を変えずにそのまま構造化して記録する準備をする
- ユーザーが話を広げたら（聞いていないことまで話し始めたら）それを妨げず、内容を記録する
- 回答が既存の記録と矛盾する場合、**AIが判断して上書きしない**。矛盾している旨をそのままユーザーに伝えて確認する
- ユーザー特有の用語（社内用語・業界用語・略語）が出たら意味を確認し、glossary.md に記録する

### Phase 4: design/ への書き出し + 確認

→ **`references/10_doc-templates.md` を読む**

対話で得られた内容を、テンプレートに従って各ファイルに振り分けて書き出す。書き出した後、必ずユーザーに要約を見せて「書き漏らし・書き間違いがないか」を確認する。修正指示があれば反映する。

- 回答が得られた issues.md の課題は、本文（該当ドキュメント）に反映したうえでステータスを「確定」にする
- 「わからない」「今は決めない」となった論点は issues.md にステータス「保留」で起票する

### Phase 5: 継続判定

ユーザーに次の問いを投げる:「他に話しておきたいことはありますか？」

- ある → Phase 2 に戻る（残っている観点カタログのトピック、issues.md の未確認課題、または自由な追加トピックから対話を続ける）
- ない（出し切った） → 終了。**観点カタログ上の未言及トピックが残っていてもそのまま終了してよい**。残った論点は issues.md に起票しておく

### Phase 6: 完了報告

以下を簡潔に報告する:
- design/ 各ファイルに書き出した内容の要約
- issues.md の「未確認」「保留」課題の一覧（次セッション・次スキルに引き継がれるもの）
- 次のステップとして [nijo-system-design](../nijo-system-design/SKILL.md) スキルに進めること（そこで design/ の要求ドキュメント群を一次インプットとして読む）

## 禁止事項

- 欠落・矛盾に対してAIが妥当なデフォルトを置いて design/ を埋めること（仮定を置いて進むのは nijo-system-design の責務）
- ユーザーが「出し切った」と言う前に、観点カタログが埋まっていないことを理由に対話を打ち切ること、または逆に無理に続けさせること
- 画面一覧・データモデル・nijo.xml など、設計に踏み込んだ提案をすること（それは nijo-system-design の責務）
- 一度に大量の質問を機械的に浴びせること（AskUserQuestion の乱発）
- ユーザーに確認せず issues.md の課題を「確定」にすること
