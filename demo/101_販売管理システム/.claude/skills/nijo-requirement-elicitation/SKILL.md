# 要求の聞き出し（要望・願望 → 要求の構造化）

未整理の要望・願望レベルのインプットを、ユーザーと対話しながら `design/wishes.md` に構造化する。

**このスキルの成果物は「要件」ではない。** 要件として完成させる作業は [nijo-system-design](../nijo-system-design/SKILL.md) の責務であり、このスキルは一切踏み込まない。

## 最重要原則（他のどのルールより優先する）

**ゴールの基準は「要件が完成すること」ではなく「ユーザーが出したい情報を全部出し切ること」。**

- 欠落・矛盾を見つけたら、AIが妥当な仮定を置いて埋めることは**禁止**。必ずユーザーに問い、ユーザー自身の頭で定義させる
- ユーザーが「わからない」「今は決めない」「後で考える」と答えたら、**そのまま「未確認」として記録する**。デフォルト値や推測で埋めない
- 完了の判定はユーザーが行う。「これで話したいことは全部話した」とユーザーが言うまでは終わらない。逆に、観点カタログ上まだ埋まっていない項目があっても、ユーザーが「もう十分」と言えばそこで終了してよい（不完全なまま終わってよい）
- 実装や設計の話（テーブル構造、画面項目、Nijoでどう表現するか等）は一切しない。あくまで「ユーザーの頭の中にある情報を言葉にして引き出す」ことに徹する

## ワークフロー

### Phase 0: 出力先の確認

出力先プロジェクトフォルダ（`design/wishes.md` の置き場所）をユーザーに確認する。既存プロジェクトの `design/wishes.md` が既にあれば読み込み、続きから対話を再開する（ゼロから聞き直さない）。

### Phase 1: インプット読解

提供された要望・メモ・会話・資料を形式を問わずすべて読む。この時点でユーザーに質問はしない。

### Phase 2: 未言及トピックの検出

→ **`references/00_topics.md` を読む**

観点カタログを1つずつ当てて、「ユーザーがまだ一度も触れていないトピック」を洗い出す。
ここでの目的は欠落を「判定」して埋めることではなく、**質問のネタを見つけること**。ブロッカー/仮定可能の分類はしない（それは nijo-system-design の仕事）。

### Phase 3: 対話

見つけたトピックについて、ユーザーに問いかける。

- 1トピックにつき1〜数問。**尋問にならないよう**、自然な会話として問いかける。全観点を機械的に一度に浴びせない
- ユーザーの回答は言い換えず、意味を変えずにそのまま構造化して記録する準備をする
- ユーザーが話を広げたら（聞いていないことまで話し始めたら）それを妨げず、内容を記録する
- 回答が既存の記録と矛盾する場合、**AIが判断して上書きしない**。矛盾している旨をそのままユーザーに伝えて確認する

### Phase 4: `design/wishes.md` への書き出し + 確認

→ **`references/10_wishes-template.md` を読む**

対話で得られた内容を `<プロジェクト>/design/wishes.md` に書き出す。書き出した後、必ずユーザーに全文または要約を見せて「書き漏らし・書き間違いがないか」を確認する。修正指示があれば反映する。

### Phase 5: 継続判定

ユーザーに次の問いを投げる:「他に話しておきたいことはありますか？」

- ある → Phase 2 に戻る（残っている観点カタログのトピック、または自由な追加トピックから対話を続ける）
- ない（出し切った） → 終了。**観点カタログ上の未確認項目が残っていてもそのまま終了してよい**。`design/wishes.md` の「未確認事項」セクションにその旨を残す

### Phase 6: 完了報告

以下を簡潔に報告する:
- `design/wishes.md` に書き出した内容の要約
- ユーザーが「今は決めない」とした未確認事項の一覧
- 次のステップとして [nijo-system-design](../nijo-system-design/SKILL.md) スキルに進めること（このスキルはそこで `design/wishes.md` を一次インプットとして読む）

## 禁止事項

- 欠落・矛盾に対してAIが妥当なデフォルトを置いて `design/wishes.md` を埋めること
- ユーザーが「出し切った」と言う前に、観点カタログが埋まっていないことを理由に対話を打ち切ること、または逆に無理に続けさせること
- nijo.xml や画面項目・データモデルなど、内部設計に踏み込んだ提案をすること（それは nijo-system-design の責務）
- 一度に大量の質問を機械的に浴びせること（AskUserQuestion の乱発）
