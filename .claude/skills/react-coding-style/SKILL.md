# React コーディング流儀

リポジトリ全体の設計原則（最小差分主義の禁止・式次第・役割語モジュールの禁止・公開面の最小化）は
[design-conventions](../design-conventions/SKILL.md) skill にあり、あちらの原則が前提である。
本流儀はそれを React に適用する際の具体的な規約であり、React 固有の判断（状態管理の優先順位・
ファイル分割・コメントの流儀など、design-conventions が定めていない事項）についてはこのファイルが正とする。
両者が矛盾する場合は design-conventions を優先する。

## 0. 規模に応じた書き分け

この流儀の柱 (状態管理の優先順位・大から小への記載順・「なぜ」コメント) は常に適用するが、
**構造面の重さは対象の複雑さに比例させる**。単純なものに重厚な構造を持ち込まない。

- **小 (〜100行程度・単機能)**: 1ファイルで完結。props 型はインライン定義。コンポーネント先頭の JSDoc に役割と使い方の前提を書く。フォルダも index.ts も型ファイルも作らない。

  ```tsx
  /**
   * 読み込み中を表すくるくる。
   * 表示中はこの裏にあるUIが操作不能になる。
   * どの範囲に覆いかぶさるかは、CSSの position:absolute で制御している。
   */
  export const NowLoading = ({ className }: { className?: string }) => {
    return (
      <div className={`absolute inset-0 ... ${className ?? ''}`}>
        {/* 半透明のシェード */}
        <div className="..." />
        {/* くるくる */}
        <div className="..." />
      </div>
    )
  }
  ```

- **中 (複数の関心事があるが1画面部品)**: 1〜数ファイル。複雑な処理だけフックに切り出す。region 区切りは本体が長くなったときのみ。

- **大 (多機能・多ファイルにまたがる複合部品)**: 専用フォルダを切り、本章以降のフル装備 (types-public/internal 分離、機能単位フック、index.ts による公開面の宣言) を適用する。

判断基準: 「この構造がないと読み手が迷うか?」。迷わないなら省く。

## 1. 状態管理と手段の優先順位（常に適用）

動作の安定性の観点から、以下の順で優れた手段とみなし、上位で書けるものを下位で書かない。

**memo・単なる導出 > state（更新はイベントハンドラで） > ref > effect**

- 既存の props / state から計算できる値は `useMemo` か単なる式で導出する。state に持たない。
  - 例: 範囲選択の「選択範囲」は、始点セルと終点セルという2つの state からの useMemo 導出にする。選択範囲そのものを独立した state にしない。
- ユーザー操作に起因する処理は、その操作のイベントハンドラの中で行う。state の更新もここで行う。effect に逃がさない。
- DOM 参照・「レンダリングに影響しない最新値の保持」は ref。
- `useEffect` は「外部システムとの同期」にのみ使う。導出計算・イベントハンドラの代替・ref で書けるものに使わない。
  - 許される例: `document.addEventListener` の登録/解除、データ件数の変化に追従して選択位置を補正する、など React の外の世界との同期。
  - effect を書くときは、何と同期しているのかをコメントで一言説明できること。説明できなければ設計を見直す。
- props を state にコピーすること、state の変化を別の state に伝搬させる effect も禁止。
- `forceUpdate` (useReducer によるカウンタ) は、外部ライブラリが React の外で値を書き換えるケースの最終手段としてのみ許す。

`useEffect` の禁止パターン（AI が特に犯しやすいもの）:

```tsx
// NG: 導出可能な値を state + effect で同期している
const [fullName, setFullName] = useState('')
useEffect(() => { setFullName(`${firstName} ${lastName}`) }, [firstName, lastName])

// OK: レンダー中に導出する
const fullName = `${firstName} ${lastName}`
```

```tsx
// NG: ユーザー操作への反応を effect に逃がしている
useEffect(() => { if (submitted) sendRequest(form) }, [submitted])

// OK: イベントハンドラで直接行う
const handleSubmit = () => { sendRequest(form) }
```

## 2. ファイル分割（大規模のとき）

- **ファイル名だけ見て、フォルダ内部の依存関係と各ファイルの役割がなんとなくわかる**粒度で分割する。細切れにしすぎない。
- 大規模な複合部品の標準構成:
  - `〇〇.tsx` — 本体コンポーネント（オーケストレーション）
  - `use〇〇.ts` — 機能単位のフック（1機能1フック1ファイル。例: useSelection / useCopyPaste / useScrollToCell）
  - 部品コンポーネント（例: CellEditor.tsx / SelectedRange.tsx）
  - `types-public.ts` — 外部公開する型。利用者向け JSDoc を丁寧に書く
  - `types-internal.ts` — フォルダ内部でのみ使う型・定数・共有ロジック。「このフォルダ内部でのみ使用」と明記
  - `index.ts` — 公開面の宣言。外部から使ってよいものだけを export
- 密結合な小さい型はそれを主に使うフックのファイルに同居させてよい。
- フォルダで名前空間を切る。`親名.機能名.ts` のようなファイル名プレフィックスによる擬似名前空間は使わない。

## 3. 複雑さの閉じ込め方

- コンポーネント本体とイベントハンドラはエントリーポイントであり、design-conventions skill 1章の式次第の原則がそのまま適用される。「何がどの順で起きるか」はコンポーネント本体を読めば分かること。
- **複雑な処理はフックに閉じ込め、呼び出し側ではフックが提供する機能の呼び出しタイミングと依存関係だけを意識すればよい**ようにする。本体コンポーネントは各フックを1行コメント付きで順に呼び、返り値を配線するだけにする。アルゴリズムの中身を本体に書かない。
- 切り出したフック / サブコンポーネントには、その仕事の内容を実装を読まずに言い当てられる名前を付ける。`useLogic`, `useHandlers`, `InnerComponent` のような、名前が仕事を表さない切り出しは禁止。
- フック間の依存はフックの引数として明示的に渡す（例: 座標計算関数 → スクロール関数 → 選択フック、という連鎖を引数で表現する）。暗黙の共有 state や context でつながない。
- 全部を1ファイル・1コンポーネント・1関数に詰め込むのも、細切れにしすぎるのもだめ。「読み手がいくつのファイルを行き来すれば1機能を理解できるか」を最小化する。
- フックの引数は、少数(〜4個程度)なら位置引数、それを超えたら単一の params オブジェクトにまとめる。

## 4. ファイル内の記載順（常に適用）

**大から小へ、全体から部分へ、概要から詳細へ。**

- コンポーネントファイル: メインコンポーネント → サブコンポーネント → 補助関数。
- フックファイル: 公開する型 → フック本体 → 内部ヘルパー関数。
- 長いコンポーネント・フックの内部は `//#region 状態` `//#region イベント` `//#region レンダリング` 等の region と区切り線で章立てする（短いものには不要）。

## 5. コメント（常に適用）

- **レイアウト(JSX)はコードが長くなりがちなので、冗長になったとしても10行ごとぐらいに、そこが UI 上のどの部分かがわかるコメントを挟む**（`{/* 列ヘッダ */}` `{/* シェード */}` 等）。これは小さいコンポーネントでも行う。
- フック呼び出しの並びにも各1行の役割コメントを付ける。
- 自明でない工夫（setTimeout を挟む理由、key の組み立て方の理由、z-index の前後関係、他モーダルとの干渉回避など）は「なぜ」をその場にコメントで残す。
- 外部公開する props・型のプロパティには利用者向け JSDoc を書く。「未指定の場合どうなるか」まで書く。責務の境界（例: 「閉じる処理は呼び出し側で実装する」）もコンポーネント先頭の JSDoc に明記する。

## 6. コンポーネント設計

- 命令的操作（選択・強制再描画・編集開始など）を外部に提供する場合は `useImperativeHandle` で明示的な Ref 型として公開する。Ref 型は公開型として定義し、各メソッドに JSDoc。
- 再レンダリングが性能に効く部品（グリッドのセル等）に限り `React.memo` + カスタム比較関数でメモ化し、**比較しない props にはその理由をコメントで書く**。「レンダリングのトリガーにのみ使用」する props はその旨を型定義に明記する。性能問題のない部品には memo を付けない。

## 7. セルフチェック

作業完了前に以下を確認する:

1. 対象の複雑さに対して構造が重すぎ/軽すぎないか（0章）。
2. state に持っているものは本当に導出できないか。effect は外部システムとの同期か。
3. 新しいファイル名だけ見て役割が推測できるか。（大規模の場合）公開/内部の境界がファイル構成で表現されているか。
4. コンポーネント本体を読んだとき、フックの中身を読まなくても処理の流れが追えるか。
5. JSX に10行ごと程度の位置コメントがあるか。自明でない工夫に「なぜ」コメントがあるか。
6. ファイル内が大→小の順に並んでいるか。

あわせて design-conventions skill 3章の共通セルフチェック（最小差分主義・役割語禁止・式次第）も実施する。
