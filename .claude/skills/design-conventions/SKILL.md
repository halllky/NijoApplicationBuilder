# 設計規約（言語非依存の設計原則）

主な読者は実装を担当する AI である。判断に迷ったら、ここに書かれた判断基準を機械的に適用すること。

適用対象は人間または AI が手で書くソースコード。
コード生成器（Nijo）が出力する自動生成コードそのものは対象外だが、
生成器のテンプレートを書く際は「生成されたコードがこの規約を満たすか」を考慮すること。

言語固有の規約は以下の skill にあり、この原則とあわせて適用する:

- C#: [csharp-coding-style](../csharp-coding-style/SKILL.md)
- React: [react-coding-style](../react-coding-style/SKILL.md)

---

## 0. 最上位原則

### 0-1. 凝集度は高く、結合度は低く

各クラス・モジュールは 1 つの関心事に責任を持ち、他のモジュールの内部事情を知らないこと。

### 0-2. 最小差分主義の禁止

「目先の指示を満たす最小の変更」で作業を終えてはならない。
**機能追加・不具合修正が終わった時点のアプリケーション全体のコードが、最も綺麗な状態になっていなければならない。**
既存の構造に継ぎ足すと歪みが生じる場合は、構造の方を直すこと。

### 0-3. 指示なしでリファクタしてよい範囲

- **今回の変更が触れたクラス・モジュール、およびその変更によって歪みが生じた呼び出し元・呼び出し先**は、
  指示がなくてもリファクタしてよい。むしろ 0-2 を満たすための義務である。
- 今回の変更と無関係な箇所の改善は、勝手に実施せず提案に留めること。
- 規約に従うと大規模な構造変更が必要になる場合は、コードを歪めて誤魔化さず、
  その旨をユーザーに報告して判断を仰ぐこと。

## 1. エントリーポイントは「式次第」である

### 1-1. エントリーポイントの定義

| アプリケーション形態 | エントリーポイント |
|---|---|
| コマンドラインアプリ | コマンドのハンドラー |
| Web サーバー | HTTP エンドポイント直下の処理（MVC なら Controller のアクションメソッド） |
| React | コンポーネント本体（レンダー部）と DOM イベントハンドラー |

### 1-2. 原則

**エントリーポイントを読むだけで「何が・どの順で起きるか」がすべて分かること。**
「プログラム」の本来の意味（式次第・次第書き）のイメージである。

- モジュール間の依存関係と処理順は、エントリーポイントが司る。
- モジュール A の内部からモジュール B を呼び、B の内部から C を呼ぶ……という
  「裏で連鎖する呼び出しチェーン」を作ってはならない。
  A → B → C の順で処理が必要なら、エントリーポイントが A, B, C をその順で呼ぶ。

### 1-3. エントリーポイントに書いてよいもの・いけないもの

書いてよい（書くべき）もの:

- 各モジュールの呼び出しと、その順序
- 「どのモジュールをどの順で呼ぶか」を決めるための分岐・ループ
- モジュール間の入出力の受け渡し・詰め替え

書いてはいけないもの:

- ドメイン計算・業務判断・データ変換の実体（→ 名詞モジュールのメソッドへ）

この結果としてエントリーポイントのメソッドが長くなることは**許容する**。
処理の流れが一望できることの方が、1 メソッドの短さより価値が高い。
逆に、エントリーポイントを短くするためだけに処理列を無名の下請けメソッド
（`ProcessCore`, `ExecuteInternal` のような名前しか付けられないもの）へ括り出してはならない。

### 1-4. 複数のエントリーポイントが同じフローを必要とする場合

- そのフロー全体に**業務上自然な名前が付く**場合
  （例:「受注を確定する」「スキーマを検証する」）は、
  該当する名詞モジュールの 1 メソッドにまとめ、各エントリーポイントから呼んでよい。
- 自然な名前が付かない場合は共有しない。
  `XxxFlow`, `XxxProcess`, `Shared○○` のようなクラスを作ってはならない。
  各エントリーポイントに式次第を書き、共有は個々のステップ（名詞モジュールのメソッド）単位で行う。

判定基準: **括り出したメソッドの名前を、実装を知らない業務側の人に言って通じるか。**
通じるなら共有してよい。通じない（実装の都合の名前になる）なら共有しない。

## 2. モジュールの命名と分割

### 2-1. 役割語モジュールの禁止

`XxxHelper`, `XxxService`, `XxxManager`, `XxxUtil`, `XxxProcessor` のような
「名詞 + 役割語」のクラス・モジュールを新設してはならない。
振る舞いは、それが属するドメイン上の名詞（C# ならクラス、React ならコンポーネント・フック）に持たせる。

役割語モジュールは「個々のファイルの見通し」は良くなるが、
モジュール数が爆発してアプリケーション全体の把握ができなくなる。
**新しいクラス・モジュールを作る前に、必ず「既存の名詞に振る舞いを追加できないか」を確認すること。**

具体的な判定手順・コード例は各言語の skill を参照。

### 2-2. 隠蔽の単位は「公開面」

- 複雑なロジックは、複数のクラス・ファイルに散らばらせるのではなく、
  特定の 1 クラス・1 モジュールの中に閉じ込めること。
- 外から見える公開メンバーは最小限にし、それぞれに意味の明瞭な名前を付けること。
- モジュールの**内部**を private メソッド・内部関数に分割するのは自由である。
  内部が長くなること自体は問題ではない。問題なのは公開面が広がること。

### 2-3. 「読み飛ばせる量」の原則

**メソッド名・引数・戻り値だけを見て「中身を読まなくてよい」と判断できるコードの量が多いほど、良い設計である。**

- メソッド名は、実装を読まなくても効果が正確に予測できる名前にすること。
- 名前から予測できない副作用（隠れた状態変更、外部への書き込み）を持たせてはならない。
- 予測できない副作用を持つなら、それは名前が間違っているか、分割の単位が間違っている。

## 3. 作業完了前のセルフチェック

タスクを完了とする前に、以下を確認すること:

- [ ] `Helper` / `Service` / `Manager` / `Util` / `Processor` という名前のクラス・モジュールを新設していないか。
      していたら 2-1 に従い名詞に振る舞いを移す。
- [ ] 新設したクラス・モジュールは、既存の名詞へのメソッド追加で代替できないか。
- [ ] エントリーポイントを読むだけで処理の全体像が分かるか。
      裏で連鎖する呼び出しチェーンを作っていないか。
- [ ] 今回の変更が触れた構造は、継ぎ足しの歪みが残っていない最も綺麗な状態か（0-2, 0-3）。
- [ ] 該当する言語別 skill（csharp-coding-style / react-coding-style）のセルフチェックを実施したか。
- [ ] 規約に従えない箇所があれば、誤魔化さずユーザーに報告したか。
