# 設計規約（C#）

[design-conventions](../design-conventions/SKILL.md) skill の言語非依存の原則を
C# コードに適用する際の具体的な規約を定める。
あちらの原則（最小差分主義の禁止、式次第、役割語モジュールの禁止、公開面の最小化）が前提であり、
この skill 単独で読まないこと。

---

## 1. クラスは名詞、振る舞いはメソッド

役割語クラス（design-conventions 2-1）を作りたくなったときの判定手順:

1. `XxxHelper` 等の名前を付けたくなったら、その `Xxx` がドメイン上のオブジェクト（名詞）である。
2. `Xxx` をクラス名とし、Helper / Service / Manager が持つはずだった責務を
   `Xxx` のメソッド（動詞）として定義する。
3. `Xxx` クラスが既に存在するなら、新しいクラスを作らずそこにメソッドを追加する。

```csharp
// NG: 役割語クラスの乱立
class OrderValidator { public bool Validate(Order order) { ... } }
class OrderPriceCalculator { public decimal Calculate(Order order) { ... } }

// OK: 名詞クラスに振る舞いを持たせる
class Order {
    public IEnumerable<string> Validate() { ... }
    public decimal CalculatePrice() { ... }
}
```

## 2. 依存の渡し方（名詞クラスに適用）

名詞クラス（ドメインオブジェクト）では:

- そのオブジェクトの**同一性・状態を構成するデータ**はコンストラクタで受け取る。
- DB アクセス・ログ・現在時刻・ファイル IO などの**外部への能力**は、
  それを必要とするメソッドの引数で受け取る。コンストラクタに注入しない。

```csharp
class Order {
    public Order(OrderId id, IReadOnlyList<OrderLine> lines) { ... } // 状態はコンストラクタ

    public void Confirm(MyDbContext db, ILogger logger) { ... }       // 能力はメソッド引数
}
```

理由: メソッドのシグネチャだけで「このメソッドが外部の何に依存するか」が分かるようにするため。

DI コンテナへの登録が前提のクラス（Controller、ホスティング関連など）は
この限りではなく、従来どおりコンストラクタ注入を使ってよい。

---

## 3. 汎用ユーティリティの例外

static クラス・拡張メソッドの集まりは、次の基準を**両方**満たす場合に限り許可する:

1. **「本来 .NET（標準ライブラリやフレームワーク）が提供していてもおかしくない汎用処理」の穴埋めであること。**
   （例: `Util.DotnetEx` は .NET が本来担うべき仕事を仕方なくこのプロジェクト内で定義しているもの。これと同レベルならよい）
2. 純粋であること: 状態を持たず、外部依存を持たず、入出力が引数と戻り値で完結すること。

このリポジトリ・このアプリケーション固有の知識（業務ルール、スキーマの意味、画面の都合）を
少しでも含む処理は、この例外の対象外である。名詞クラスのメソッドとして定義すること。

## 4. コメント

- 一時的情報や変更経緯をコメントに書かないこと。修正後のコメントがあたかも最初からそうであったかのように書くこと。
- XMLドキュメントにシンボルの名前を書くときは `<see cref="">` で参照すること。IDEによる参照元検索を効かせるため。
- 定数の値や具体的な他のソースコードのファイル名など物理的名称を極力コメントに書かないこと。リファクタリングの際に変更漏れを引き起こすため。
- そのモジュールが知っている範囲を超えた記述は極力コメントにも書かないようにすること。コメントの修正漏れが起きやすくなるため。
  - 例: データの保存を行なっていないクラス SomeCalculator.cs につけるコメントの例
    - OK: データの保存はこのクラスでは行わない。
    - NG: データの保存はこのクラスを呼び出している SomeController.cs 側で行う。（SomeController から SomeCalculator への依存関係はあるが逆方向への依存関係は存在しないので、コメントにも Controller の存在を書かない）

## 5. セルフチェック

design-conventions skill 3章の共通セルフチェックに加えて:

- [ ] 名詞クラスで、外部への能力（DB・ログ・時刻・IO）をコンストラクタ注入していないか（2章）。
- [ ] 新設した static クラス・拡張メソッドは、3章の 2 基準を両方満たすか。
